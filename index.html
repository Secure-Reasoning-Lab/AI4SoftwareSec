About the workshop

How can advanced AI systems help us understand, assess, and improve software security?

Software security demands capabilities that are hard for any AI system: reasoning about program behavior, finding failures that existing tests miss, and fixing them without breaking intended functionality.

AI for Software Security (AI4SoftwareSec) brings together researchers in machine learning, computer security, software engineering, and program analysis to build a shared research agenda across the software lifecycle.

Through talks and discussions, we will compare methods, share deployment experience, and develop evaluations that measure real security improvements.

Research directions

From program understanding to practical security improvements.

01

Vulnerability discovery & verification

Security-aware code representations, learned fuzzing and harness generation, static and dynamic analysis, symbolic reasoning, and validation of candidate flaws in authorized environments.

02

Repair & hardening

Security patch generation and validation, migration to memory-safe languages, formal verification, and proof synthesis.

03

Secure code & software supply chains

Security of AI-generated code, binary analysis and reverse engineering, malware detection, and malicious-package detection.

04

Learning & reasoning for security agents

Reinforcement learning, preference optimization, training data, long-horizon planning, tool use, uncertainty calibration, and efficient inference-time compute.

05

Evaluation & deployment

Benchmarks, generalization to unseen projects, cost-aware comparisons, human oversight, responsible disclosure, and adoption by software maintainers.

Our focus is AI methods that improve software security. The security of AI agents is in scope when it affects their ability to analyze untrusted code or safely operate security tools.

Contribute

Call for papers

Planned · not yet open

We welcome learning algorithms, systems, empirical studies, benchmarks, and position papers on AI for software security. The planned workshop is non-archival, with submissions and reviews managed through OpenReview.

Research papers

Up to 8 pages

Research contributions supported by clear methods, sound evaluation, and evidence of relevance to software security.

Short papers

2–4 pages

Focused experiments, negative results, replications, preliminary methods, and well-supported positions.

Page limits exclude references and appendices. Both tracks will use the ICLR 2027 paper format. The main text must contain the evidence needed to assess the contribution.

Review process & presentation

Each submission will receive three reviews in a double-blind process. Reviewers will assess relevance, technical soundness, clarity, strength of evidence, and contribution to discussion, taking each paper’s stated scope into account.

All accepted papers will receive a poster slot. Six papers will be selected for oral presentation based on quality, relevance, and potential to stimulate discussion. Short papers are eligible for oral presentation.

Evaluation & responsible research

Empirical papers should describe software versions and evaluation environments, model access and budgets, baseline configurations, data separation, and limitations. Vulnerability counts should distinguish unique root causes from duplicate reports. Patch success should distinguish removal of a reproducer from broader security and regression checks.

Artifact release is encouraged, with responsible handling of sensitive results and coordinated disclosure where appropriate.

Non-archival & concurrent submissions

We welcome work in progress and substantive extensions or reanalyses. Already published papers without a new contribution are outside the call. Concurrent submissions must comply with the other venue’s policies.

Use of large language models

LLMs may be used as general-purpose assistance tools. Substantial contributions to research ideation or writing must be disclosed in a separate “LLM Usage” section, typically in the appendix and excluded from the page limit. Failure to disclose significant use may result in desk rejection. Authors are responsible for all content; LLMs cannot be credited as authors.

Short papers must be primarily human-authored and reflect the authors’ own thought and analysis. AI assistance is permitted, but AI-generated short papers are not allowed.

Submissions are not open yet. The OpenReview link and final submission instructions will be announced here.
